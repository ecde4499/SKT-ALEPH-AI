01 / OVERVIEW

무엇을 만들었나요?

위험한 주소를 곧바로 차단하는 것이 아니라, URL 근거와 차단 범위를 확인하고 승인된 정책을 적용하는 보호 구조를 설계·구현했습니다.

PROBLEM

주소는 비슷해도 사이트는 다릅니다.

기관·법무법인을 사칭하는 피싱 주소는 겉보기만으로 판단하기 어렵습니다. 반대로 근거가 불충분한 주소를 무조건 차단하면 정상 서비스까지 막을 수 있습니다.

APPROACH

탐지와 차단 사이에 검토를 둡니다.

외부 위협 정보에서 후보를 수집하고, 정책 엔진이 판단 근거를 제안합니다. 사람의 승인·정책 서명과 DNS 적용을 분리해 과차단과 잘못된 집행 위험을 낮추도록 했습니다.

03 / MY CONTRIBUTION

POLICY ENGINE / PERSONAL ROLE

차단과 경고의 조건을 구분했습니다.

기존 정책 엔진에서 관리자 승인·명시적 차단 근거가 있는 BLOCK과 점수 기반 WARN, 정상 허용 ALLOW, 근거 부족 UNKNOWN을 구분했습니다. 위험도 판단 기준 8개를 별도 제안 모듈로 만들고, 정보가 부족할 때 무리하게 ALLOW로 처리하지 않도록 했습니다.

① URL 위험도 기준 정리

등록된 지 얼마 안 된 도메인, 검증된 피싱 신고, 악성 IP·CNAME 연관 등 총 8개 위험 기준을 정리했습니다.

② 기존 정책 엔진과 연결 검토

별도 위험도 점수 제안이 기존 정책 판단에 어떤 형식으로 전달될지 수동 검토용 연결 코드를 구성했습니다. 운영 자동 집행 기능으로 연결하지 않았습니다.

③ 팀 협업과 발표 준비

DNS 담당 팀원과 판정 결과 전달·차단 범위를 검토하고, 위협정보·정책 판단을 설명하는 발표 내용과 예상 질문을 정리했습니다.

05 / WHAT I LEARNED

차단보다 먼저 확인해야 할 것

범위와 근거를 구분하기

URL 하나에 대한 신고가 도메인 전체 또는 하위 모든 서비스의 차단 근거가 되는 것은 아닙니다. 그래서 공식 출처, 도메인 범위, 유효기간과 검토 절차를 확인했습니다.

테스트 결과를 과장하지 않기

합성 DNS 응답 일치와 실제 피싱 사이트 탐지율은 서로 다른 평가입니다. DNS 우회 경로, 단말 캐시, 공유 호스트의 과차단 영향도 별도 검증이 필요합니다.
